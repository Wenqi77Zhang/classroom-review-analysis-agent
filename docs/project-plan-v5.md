# 课堂复盘与教学分析 Agent：四天五人执行规划 v5

> 适用范围：课堂复盘与教学分析 Agent
> 团队：5 人，技术水平接近，后端使用 Python，前端技术不限
> 组长：成员 1
> 前置阶段：成员 1 以组长身份与 Codex 在四个开发日之前共同完成，不计入四天开发工时
> 成员投入：每人约 24 小时，共约 120 人时，集中在 4 天完成
> 最终交付：可直接访问的网页、完整源代码与部署说明、1 份小组报告
> 规划原则：网页要求是硬性验收基线；里程碑 M1 全链路优先；不把模拟内容描述成真实功能

---

## 1. 需求结论与范围边界

### 1.1 产品定位

面向需要复盘一节公开课并形成改进方案的高校教师。教师上传课堂视频、课件或逐字稿后，系统从真实视频生成带时间点的逐字稿；对英文或中英混合内容同时保留英文原文和逐句中文译文；系统生成区分“事实、判断、建议”的教学分析，每条结论连接视频、原文、课件页或画面证据；只有经教师接受或修改确认的内容才能进入最终报告。

### 1.2 使用边界

- 系统辅助教师复盘，不替学校自动给教师打分。
- 没有证据的判断不得进入最终报告。
- 只上传现成逐字稿不能替代真实视频处理链路。
- 视频必须持久保存到对象存储，不能依赖教师电脑、浏览器缓存或部署服务器本地目录。
- M1 默认对象存储确认采用 Backblaze B2 私有 Bucket，并通过可替换的 S3 Provider 接口接入；不得让业务层绑定单一供应商。
- 数据库保存文件信息、对象地址、所属教师、课程、课堂、任务和处理状态，不保存视频二进制。
- 更换输入后必须重新运行并产生与新输入对应的结果，不能使用写死内容或固定录像。
- 如果某项仅为界面原型或模拟功能，必须显著标注，并在报告中如实归入“部分实现”或“尚未实现”。

### 1.3 四天承诺范围

必须完整完成里程碑 M1：

1. 对话发起复盘任务并追问范围、重点和判断条件。
2. 上传真实课堂视频、课件或逐字稿。
3. 显示真实上传和处理状态，失败可重试。
4. 从视频实际生成带时间点的逐字稿。
5. 英文或中英混合课堂显示英文原文和逐句中文译文。
6. 教师可修改文字、说话人和译文。
7. 生成区分事实、判断和建议的教学分析。
8. 每条结论能跳转到视频、原文、课件页或画面证据。
9. 教师可接受、修改或驳回结论，保留修改内容和确认状态。
10. 只组合已复核内容，支持报告编辑、预览和导出。
11. 使用第二段不同视频验证能够重新分析。
12. 完成部署、源码、README、配置说明和小组报告。

暂不承诺：

- 里程碑 M2——第二轮课堂改进对比：属于进阶项，仅在里程碑 M1 全部通过后评估。
- 里程碑 M3——多门课管理：可选。
- 脑图或知识图谱：可选。

差异化亮点不另起支线，而是嵌入里程碑 M1：

- “分析契约”对话：处理前确认范围、指标、证据条件和隐私模式。
- “证据工作台”：播放器、逐字稿、课件与分析卡片四联动。
- “证据账本”：记录模型、Prompt、Skill、证据和教师修改版本。
- 两类学科 Skill：计算机/AI 课程、人文社科课程。
- 隐私路由：公开课可使用免费云模型；私有课堂默认本地处理。

### 1.4 术语约定

- `里程碑 M1`：四天内必须完成的单节课堂全链路。
- `里程碑 M2`：只有里程碑 M1 全部通过后才评估的第二轮课堂改进对比。
- `里程碑 M3`：可选的多门课程管理。
- `成员 1` 至 `成员 5`：五位团队成员的编号；文件树和责任表中不得缩写成 `M1` 至 `M5`。
- “M”只用于 Milestone（里程碑），不用于 Member（成员）。

## 2. 阶段 0：成员 1（组长）与 Codex 共同完成的项目准备

阶段 0 必须在四个集中开发日开始前完成。它不是五个开发责任包之一，由成员 1 以组长身份代表团队作决定并验收，Codex 协助整理和搭建。阶段 0 不计入成员 1 的 24 小时开发工时；成员 1 可以在小组报告中如实说明其范围确认、仓库组织和人工审核贡献，但不得把 Codex 生成的方案、模板或骨架冒充为个人独立技术实现。

### 2.1 阶段 0 的职责边界

成员 1（组长）负责：

- 代表团队确认最终产品范围、分工原则和人工决策。
- 确认 GitHub 仓库归属、可见性和成员名单。
- 审核数据来源、许可、隐私模式和外部服务注册方式。
- 对最终方案和空项目结构作人工确认。
- 冻结第一版需求、接口与目录责任边界；开发期间控制范围，避免临时增加里程碑 M2 或里程碑 M3。
- 确认成员 2–5 能够从仓库文件中读懂自己的输入、输出、依赖和验收标准。

Codex 负责协助：

- 把网页要求整理为需求基线和验收矩阵。
- 将确认后的产品、技术、Agent、数据、安全和测试方案写成项目文件。
- 创建 GitHub 仓库或指导完成授权连接。
- 搭建由空目录、占位文件、最小配置和说明文件组成的项目骨架。
- 为每个待开发目录和关键文件写明负责人、任务、输入输出和完成定义。
- 创建协作规范、Issue/PR 模板、测试模板和 AI 协作记录模板。
- 检查仓库不包含视频、密钥、账号、Cookie 或其他敏感信息。

#### 跨平台一键入口的完成标准

`setup.ps1` 与 `setup.sh` 必须：

1. 检查 Git、Python、Node.js/npm 和 FFmpeg 是否存在以及版本是否兼容。
2. 在仓库根目录创建 `.venv`，不能把 Python 包安装进系统环境。
3. 安装 `pyproject.toml` 中的后端、Worker、Agent 和测试依赖。
4. 安装 `frontend/package.json` 中的前端依赖。
5. 在本地配置不存在时，由 `.env.example` 复制出待填写配置；不得覆盖已有配置，不得自动填入真实密钥。
6. 检查 PostgreSQL、Backblaze B2/S3 Provider 和模型相关配置；Docker 仅为可选的本地基础服务方案。
7. 调用对应的 `verify` 脚本执行最小环境与冒烟验证。
8. 可以安全重复执行；已存在的 `.venv`、依赖和本地配置不能被破坏。
9. 缺少系统级工具时停止并给出针对当前操作系统的明确安装提示，不静默申请管理员权限。

`start.ps1` 与 `start.sh` 必须：

- 启动前端、FastAPI 后端和 Worker，并显示各服务地址、进程状态和日志位置。
- 启动失败时指出失败服务和排查入口；不能只弹出窗口后无提示退出。
- macOS/Linux 脚本需要在 README 中说明首次执行 `chmod +x setup.sh start.sh verify.sh`。

`verify.ps1` 与 `verify.sh` 必须：

- 检查 `.venv`、Python 包、Node.js 依赖、FFmpeg、配置文件和关键端口。
- 执行后端健康检查、Worker 冒烟、Agent Schema 测试和前端最小测试。
- 返回明确退出码：全部通过为 `0`，任一必要检查失败为非 `0`。
- 输出不得包含 API Key、Cookie、访问令牌、数据库密码或对象存储签名 URL。

#### M1 对象存储选型（2026-07-26 已确认）

- 默认实现：Backblaze B2 私有 Bucket，使用其 S3 兼容 API；选择原因是可在免费额度内开始验证、不要求先绑定付款方式、支持大文件、预签名 URL、CORS、生命周期规则和受限应用密钥。
- 可替换边界：后端与 Worker 只依赖统一 `ObjectStorageProvider` 契约；B2 endpoint、region、bucket 和应用密钥全部通过环境变量注入，不写入仓库。
- 权限边界：成员 3 负责生成限对象、限操作、默认 15 分钟有效的预签名 URL，并验证账号与对象归属；浏览器不得获得长期应用密钥。
- 数据边界：成员 4 通过 Provider 读取原始视频并写回派生文件；数据库仅保存对象键、归属、版本、校验值、大小、类型和处理状态。
- 隐私边界：M1 只上传有来源与许可记录的公开课演示数据，Bucket 保持私有，对象键使用不可猜测 ID；默认保留 7 天并验证删除与审计。
- 成本边界：免费额度是演示约束而非无限资源；接近容量或下载限额时停止新增数据，不自动开通付费，也不把计费凭据交给代码。
- Worker 失败可以从阶段断点重试；Agent 不得绕过证据门禁，也不得直接修改教师确认状态。

实际骨架可以在技术方案冻结后调整，但必须满足：

- `OWNERSHIP.md` 集中列出每个目录、文件、负责成员、任务和交付证据。
- `.github/CODEOWNERS` 为目录设置自动审查责任。
- 根目录保留唯一的 `README.md` 作为仓库总入口；每个模块使用职责明确且不重名的说明文件，并写明目的、负责人、输入、输出、接口、依赖、测试和完成定义。
- 空文件不冒充实现，统一标注 `TODO` 或使用 `.gitkeep`。
- `.env.example` 只写变量名和说明，不写真实密钥。
- 项目方案文件与仓库结构保持一致；任何结构变化都同步更新方案和责任表。

## 3. 新增要求：四阶段研发路径与评分导向

项目必须按以下顺序推进，不能从功能清单或技术选型直接开始：

必须形成：

- 产品定位。

总分 100 分：

- 实际交付内容 60 分：

## 5. Agent 模式定案

系统不采用一个无限循环的纯 ReAct Agent，而采用混合架构：

```text
教师对话
  ↓
分析契约（范围、指标、证据条件、隐私模式）
  ↓
确定性媒体状态机
  ↓
带时间戳逐字稿、双语翻译、课件页
  ↓
协调器制定一次分析计划
  ↓
多个教学分析 Skill 并行执行
  ↓
证据校验器
  ↓
教师人工复核
  ↓
已确认内容进入报告
```

- Perceive–Reason–Action–Learn：作为产品级框架。
- Perceive：读取视频、逐字稿、课件、教师目标和复核状态。
- Reason：制定分析计划、选择 Skill、生成事实/判断/建议。
- Action：调用检索、时间定位、课件定位、证据校验和报告工具。
- Learn：只记录教师接受、修改、驳回形成的显式偏好；不自动修改模型或评分标准。
- ReAct：仅用于对话追问与有限工具选择，限制轮数和工具范围。
- ReWOO 思路：确认分析契约后一次规划，并行执行分析模块，最后统一校验，降低重复推理和成本。
- Human-in-the-loop：教师确认是进入报告的强制审批门。
- MCP：四天版本不为展示概念强行接入；未来连接高校课程库、网易课程平台或外部文档系统时再使用。

## 9. 发布门禁

以下任一项不通过，不允许标记里程碑 M1 完成：

- 视频没有进入对象存储。
- 逐字稿不是由视频实际生成。
- 页面进度为模拟计时器。
- 更换输入后仍出现固定结论。
- 结论没有时间、原文、课件页或画面证据。
- 未复核或已驳回结论进入报告。
- 教师修改内容或状态没有持久保存。
- 英文样例没有同时保留英文原文和逐句中文译文。
- 无法从结论跳回播放器证据片段。
- 页面只能在开发者讲解下操作。
- 手机端出现明显遮挡。
- 登录账号之间数据混淆。
- 密钥出现在前端、仓库或日志。
- README 无法指导其他人启动。
- 没有一组非预置输入的真实试用记录。
- 没有记录试用问题、原因、修改和再次运行结果。
- 四阶段产出缺失或直接从技术选型跳到实现。
- AI 协作记录没有关键提示词、AI 结果、人工核验和修改原因。
- 任一成员无法指出自己的可核对成果、测试或协作贡献。
- 报告把模拟、部分完成或尚未实现写成已实现。

严重问题单独阻断提交：

- 产品链接无法访问。
- 源码或报告缺失。
- 核心流程无法运行。
- 抄袭、伪造来源或伪造结果。
- 把模拟内容冒充真实运行。

最终发布前由成员 5 按 100 分评分表完成一次自评；成员 3 复核后端与部署的技术真实性，成员 4 复核数据来源与证据，成员 2 复核前端实际呈现，成员 5 复核 Agent、测试和“已完成”声明；成员 1 以组长身份复核用户价值、产品方案、报告一致性并作最终人工确认。
